# Mark 56 Android Companion

Buildable Android pairing client (Phase 7B). Open this directory in Android Studio with JDK 17 and Android SDK 35, or run `gradle :app:assembleDebug`. CI builds and uploads the debug APK as an artifact; this is not a Play Store release.

## Pairing
1. Start the desktop HTTPS companion service on a trusted LAN using a certificate whose SAN includes the desktop IP.
2. In Mark 56, create a one-time pairing offer with explicitly approved scopes and display a QR generated by `build_pairing_payload`.
3. Install the APK, tap **Scan pairing QR**, and scan the desktop QR.
4. The app verifies the QR-provided SHA-256 certificate fingerprint before sending the one-time code. The bearer token is stored using Android Keystore-backed AES-GCM.

## Current limits
QR pairing, Keystore-backed credential storage, opt-in battery reporting, notification forwarding and scoped Android MediaSession polling/execution are implemented in the companion source. Physical-device validation is still required for each Android version and media app. Desktop UI controls for queueing media actions, reconnect UX and certificate rotation UX remain separate acceptance tasks. Production APK signing and publishing are automated by the protected `Signed Android Companion Release` workflow. Disconnect clears the local token; revoke the device in JARVIS to invalidate its server-side token. Do not expose the listener publicly.


## Phase 7C — opt-in battery reporting

After pairing, the app stores the desktop endpoint, certificate fingerprint and device ID alongside the encrypted bearer token. Battery reporting is **off by default**. The owner must tap **Enable battery sync** in the phone app; the app then schedules a WorkManager update no more frequently than every 15 minutes while network connectivity is available.

Each battery report contains only the integer battery percentage and a charging boolean. Requests are signed with the enrolled device token using the desktop HMAC-SHA256 canonical JSON contract, and sent over the same certificate-pinned HTTPS connection. No location, contacts, SMS, microphone, camera, notification text or health data is collected by this feature. Disconnect cancels the scheduled work and clears the local credential and connection metadata; revoke the device in Mark 56 to invalidate its server-side token.

Battery sync requires that the desktop pairing offer approved `battery.read`. If that scope was not approved, the control remains unavailable. WorkManager's 15-minute interval is a minimum scheduling interval, not an exact delivery guarantee; Android may defer updates for battery optimization or connectivity.


## Phase 8 — notification relay (owner opt-in)

Notification forwarding is now available as a separately opt-in companion feature. Before pairing, tap **Request Notification Scope** in the companion to request the desktop-approved `notification.receive` scope as part of the QR enrollment. After the desktop approves the scope and pairing completes, enable notification relay separately. The desktop owner must approve that scope in the pairing offer. The app then opens Android's Notification Access settings; the OS-level access grant is required as well.

When both approvals are present, only the displayed app label, notification title, notification text and event timestamp are forwarded. Delivery uses HMAC-SHA256 signed requests over the same TLS certificate-pinned desktop connection. Relay remains disabled unless the user toggles it on in the app. The user can disable forwarding in the app at any time or revoke Android Notification Access from system settings. If scope approval was missed, pair again with the scope approved.

Notification contents can contain sensitive personal information. This feature is intentionally opt-in at both the desktop pairing and Android OS levels; do not enable it on shared devices or relay notifications to an untrusted desktop.


## Phase 7E — opt-in Android media controls

Media control is a separate permission. Before pairing, tap **Request Media Control Scope** so the Android client requests media.control in the QR enrollment. The desktop owner must approve it. After pairing, tap **Enable Media Controls**. Android Notification Access is required so the companion can discover active media sessions; the app opens the system settings page when this access is missing.

The companion polls the desktop's authenticated media queue over pinned HTTPS every five seconds while its notification-listener service is connected. Only play, pause, play/pause, next, previous and stop are accepted. A command is executed only when exactly one eligible active media session exists; multiple active sessions are treated as ambiguous and left untouched. Media controls are off by default and can be disabled immediately in the app.

See [Phase 7E implementation and validation notes](../docs/ANDROID_MEDIA_CONTROLS.md). This is not a remote-control or arbitrary-device-command channel. Physical-device verification remains required.


## Phase 8 — Wear OS companion

The Gradle project now contains a separate `wear-app` module. Install the
phone and watch debug APKs from the same CI run, pair the watch to the phone
with Wear OS, request `command.send` before desktop pairing, and explicitly
enable the phone's Wear OS bridge. The watch exposes a small quick-action
surface (play/pause, next, previous, JARVIS ping). The phone forwards only
those allowlisted actions over the signed, certificate-pinned desktop channel.
The desktop Devices panel displays received watch events; it does not execute
them automatically.

See [Wear OS Phase 8](../docs/WEAR_OS_PHASE_8.md).

## Phase 9 — smart-glasses adapter framework

`core/glasses_adapters.py` defines a vendor-neutral adapter contract with
capability declarations, per-device scope checks, explicit per-session
consent, payload limits, and immediate consent revocation. Real vendor SDK
connectors are not bundled until a supported glasses model and SDK access are
selected. See [Smart Glasses Adapters](../docs/SMART_GLASSES_ADAPTERS.md).

## Phase 10 — secure remote relay

The optional relay is in `relay/`: a SQLite hashed-credential registry,
ephemeral FastAPI WebSocket broker, one-time provisioning CLI, Docker Compose
deployment behind Caddy TLS, desktop outbound connector, and Android TLS
WebSocket client. Both endpoints must be provisioned with distinct
least-privilege credentials in the same channel. Messages are not persisted.
See [Secure Remote Relay](../docs/SECURE_REMOTE_RELAY.md).

The Android remote-relay screen is opt-in and connects while the companion
activity is active; a persistent background connection service is not claimed.
The desktop Devices page can now save a separate desktop relay token in the
operating-system keyring and start/stop an outbound relay connection. Incoming
events are held as bounded, in-memory metadata and are not automatically
executed. Deployment to an owner-controlled host and application-owned desktop
event-handler wiring remain acceptance tasks.

## Phase 11 — production signing and release integration

The app and watch modules have minified, resource-shrunk release build
variants. The `Signed Android Companion Release` workflow tests both modules,
builds both APKs and Play-ready AABs from a `companion-v*` tag, checks package
IDs and version names, verifies APK alignment, and confirms that every APK/AAB
is signed by the exact certificate exported from the owner-managed keystore.
It publishes SHA-256 checksums and fails closed if any signing secret or
verification step is missing or invalid. The workflow requires four
owner-managed GitHub Actions secrets; no signing key is stored in this
repository.

A stable owner-signed release has been published as
[`companion-v1.1.3`](https://github.com/ibarakumo2000-stack/Mark-56/releases/tag/companion-v1.1.3).
The Jarvis website selects the latest stable versioned companion release and
does not offer the rolling debug/testing preview as a public APK. To publish a
new release after merging companion changes, push the next version tag (for
example, `git tag companion-v1.1.4 && git push origin companion-v1.1.4`).

See [Android Release Signing](../docs/ANDROID_RELEASE_SIGNING.md) and
[Android Companion Polish](../docs/ANDROID_COMPANION_POLISH.md).
